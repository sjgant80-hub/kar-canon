Start here

Kar-Canon tells you whether two JSON documents carry exactly the same data, however they are formatted, and where they differ when they do not. It runs entirely in this page: nothing you paste is sent anywhere, and no AI judges anything.

  1. Paste document A and document B above, or press one of the Load example buttons.
  2. Press Canonicalize & compare.
  3. Read the verdict: MATCH means the same data; DIFFER lists every path where a value was added, removed or changed.
  4. Keep the fingerprints: the SHA-256 of each canonical form, which anyone can recompute.

What this proves

AI pipelines re-serialize the same structured decision (a tool call, a policy verdict, a cached response) through different libraries, languages, and formatters. Key order shifts, whitespace changes, 1.50 becomes 1.5 — and a naive string or byte comparison flags a false mismatch, or worse, a naive "looks similar" check misses a real one.

kar-canon converts each document to a single, fully-specified canonical byte string (closely following RFC 8785, the JSON Canonicalization Scheme), hashes it with SHA-256, and compares hashes. Anyone — in any language — can re-implement the algorithm below and reproduce the identical hash from the identical data. There is no model in the loop and nothing to trust but the arithmetic.

Honest limits

  • Not schema validation. This does not check whether a document is well-formed as an API contract expects (that's a JSON Schema conformance job) — only whether two documents are byte-for-byte the same once whitespace, key order, and number spelling are normalized.
  • Arrays stay order-sensitive, on purpose. ["a","b"] and ["b","a"] are different data and will correctly report DIFFER. Only object key order is normalized, because JSON objects are unordered maps and arrays are ordered sequences.
  • Numeric precision follows JavaScript doubles. Integers beyond 253 may lose precision during parsing, same as any tool built on JSON.parse. If a value's exact precision matters (large IDs, monetary minor units beyond safe-integer range), carry it as a string in your JSON, not a bare number.
  • Duplicate object keys resolve last-value-wins, matching standard JSON.parse behavior. The JSON spec itself does not mandate this — a different parser could legally pick first-wins. Don't rely on duplicate keys in data you intend to canonicalize.
  • No Unicode normalization. é as one code point (U+00E9) and é as "e" + combining accent (U+0065 U+0301) are different strings and will correctly report DIFFER, even though they render identically. That is a deliberate choice, not a bug — but it can surprise you.
  • Cross-language re-derivation needs care. Some JSON libraries (e.g. Python's default json.dumps) escape non-ASCII characters unless told not to. To reproduce this tool's hash elsewhere, make sure your serializer emits raw UTF-8 for non-ASCII text, matching the algorithm below.
  • This implementation has not been run against the full RFC 8785 conformance suite — treat it as "closely aligned," not a certified implementation.
Algorithm — reproduce this hash yourself
  1. Parse the input as JSON (RFC 8259). Reject on parse failure.
  2. Canonicalize recursively:
    • null, true, false → the literal token.
    • number → the ECMAScript Number::toString form (shortest round-tripping decimal any compliant JS engine produces); negative zero canonicalizes to 0.
    • string → a JSON string literal with only the mandatory escapes (", \, and control characters U+0000–U+001F); every other code point is emitted as literal UTF-8, unescaped.
    • array → [ + canonicalized elements, comma-separated, original order preserved + ].
    • object → keys sorted by UTF-16 code unit order, duplicates resolved last-wins, then { + "key":value pairs, comma-separated, no extra whitespace + }.
  3. UTF-8 encode the resulting canonical string.
  4. SHA-256 the bytes; render the digest as lowercase hex.

    How it works
    
  
  
    1. Each document is parsed and rewritten in one canonical form, aligned with RFC 8785: keys sorted, every number and string in one spelling, no whitespace.
    2. Each canonical form is hashed with SHA-256. Equal hashes mean equal data, whatever the formatting, key order, number spelling or escapes.
    3. When they differ, it walks both documents and lists every path where they part.

    Where it stops, answered straight
    
  
    • Arrays are compared in order, by design. ["a","b"] and ["b","a"] DIFFER.
    • Very large or very precise numbers. Integers beyond 2^53 and decimals with more than about 17 significant digits are compared after rounding to the nearest double.
    • Not the full RFC 8785 suite. It has not been run against the complete conformance suite.
    • Sameness, not correctness. It does not check either document against a schema; kar-conform does.

    FAQ
    
  
    Is it the same as a text diff?
    No. A text diff compares characters; this compares data. Two files that differ only in formatting, key order or number spelling MATCH.
    Can an agent run it?
    Yes. The same kernel ships as a one-file Node.js script (scripts/kar-canon.mjs) with no dependencies, usable as an agent skill or a CI step.
    Does it need the internet or an account?
    No. The page works once loaded, and the script runs offline. Nothing is uploaded.
